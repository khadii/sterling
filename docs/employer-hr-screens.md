# Employer dashboard, departments, roles, calendar and activity

## Install

Apply migrations **0013 → 0014 → 0015 → 0016** after existing migrations 0001–0012, then build/redeploy the backend. The new HR tables start empty. Existing workspace memberships are not converted into employment records because membership does not tell us a hire date, salary, job position or leave entitlement. No existing users are deleted or re-registered.

This implements employer-managed HR records for the supplied screens. It does **not** introduce another employee account-registration flow. AI descriptions, AI skill suggestions and structured skill groupings are excluded. Existing projects/tasks and the five-step role wizard remain in use.

Requests use `Authorization: Bearer <access_token>`. The backend resolves the workspace from membership. Omit `organizationId`; use `X-Organization-Id` only when the signed-in user has multiple workspaces. All identifiers are generated by the backend except references to existing records that the frontend selects.

All paths below have the `/api/v1` prefix. Swagger exposes request examples, scalar query parameters, and response schemas.

Uploaded subteam icons use `iconId`, referring to the same department-icon catalogue used by the icon picker. Use the catalogue's returned signed `url` and `builtinKey`; do not build storage URLs yourself. Referenced subteam icons are protected from permanent deletion before storage files are removed.

## Calculation rules

Counts are computed from the complete workspace dataset, **not the current paginated page**. Existing member access-role assignments are not treated as employee headcount.

| Value | Definition |
|---|---|
| Headcount | HR employment has started and has not ended on the selected workspace-local date. End dates are inclusive. |
| Previous headcount | Same date one calendar month earlier. Department transfer history prevents transfers rewriting the old department total. |
| Growth | `(current − previous) / previous × 100`; `null` if previous is zero. |
| Staffing plan | Sum of open requisition `positions` for the role: **target total positions**, not extra vacancies to add to existing staff. |
| Filled/open | Active employee job-role assignments; `open = max(target − filled, 0)`; `total = max(target, filled)`. |
| Average salary | Arithmetic mean of supplied annual salaries among role holders, grouped by currency; zero salaries count. Missing salaries are excluded and `sampleSize` is returned. Historical salary averages are unavailable because salaries are not historical snapshots. Requires `payroll.view`. |
| Team capacity | Active employees linked to the team / planned capacity × 100. Can exceed 100 for overstaffing. Understaffed means filled < planned. |
| Attendance | Only approved attendance counts. Present and late both contribute to department attendance %. An unrecorded day is not silently classified absent. |
| Budget utilization | Annual base-salary commitment in the budget currency / annual personnel budget × 100. This is **not actual cash spending**. Missing salaries, unmatched currencies, historical dates or zero budget produce `null`, with missing-record count returned. |
| Checklist | Completed items / all items × 100; an empty checklist returns 0%. |
| Leave | Inclusive Monday–Friday days; weekends excluded. Current policy does not subtract public holidays or implement individual shift calendars. A request must stay within one calendar year; split cross-year leave into two requests. |
| Leave balance | Explicit employee/year/type entitlement minus approved leave. Cancelled/declined requests do not consume balance. Role `leaveDays` is policy information; assign the employee's actual yearly entitlement explicitly. |
| Payroll | Per-period gross minus deductions; sum using database decimal arithmetic. Different currencies are never summed together. Finalization validates employee coverage and all submitted timesheets; it does not infer missing timesheets. |

A genuine result of **0 is returned as `0`**, including headcount, vacancies, salary averages, payroll totals and checklist progress. `null` means the quantity cannot be calculated or the caller cannot access it. Frontend rendering should use `value ?? '—'`, **never** `value || '—'`.

Example with no employees:

```json
{
  "headcount": 0,
  "previousHeadcount": 0,
  "headcountChange": 0,
  "headcountGrowthPercent": null,
  "openRoles": 0,
  "onLeaveToday": 0,
  "pendingApprovals": 0
}
```

`operationalStatus` is an explicit HR planning label (`stable`, `growing`, `at_capacity`, `optimized`), not a fabricated performance score.

## Populate source data

Create an HR record for an **existing workspace member**:

`POST /employer/hr/employees`

```json
{
  "userId": "152d8fe4-4c96-4e1f-a336-88fa60762587",
  "departmentId": "c56e6a9b-b44c-40ee-9d05-ab5090d8cc39",
  "roleId": "da0ea39c-2cbb-4216-a460-e65b8b349c53",
  "startsOn": "2026-09-21",
  "annualSalary": 80000,
  "currency": "USD"
}
```

The response returns the generated employee `id`; use it for the HR endpoints below. `roleId` here is the employee's job position. It does **not** grant access permissions. Keep the existing `/organization/roles/:id/permissions` and `/organization/members/:userId/roles` APIs for permission-checked access grants. A user cannot grant permissions they do not hold.

| Create source | Request |
|---|---|
| Day-one checklist | `POST /employer/hr/onboarding/:employeeId` with `checklist: [{title, completed}]`, `buddyUserId?`, `hardwareStatus`, `welcomePackStatus`, `hrNotes?` |
| Entitlement | `POST /employer/hr/entitlements/:employeeId` with `{year: 2026, leaveType: "annual", days: 25}` |
| Leave | `POST /employer/hr/leave` with `{employeeId, leaveType, startsOn, endsOn, reason?}` |
| Attendance | `POST /employer/hr/attendance` with `{employeeId, date, state: "present", hours: 8}`. Absent records must have zero hours. |
| Review | `POST /employer/hr/reviews` with `{employeeId, reviewerUserId, dueOn, notes?}` |
| Expense | `POST /employer/hr/expenses` with `{employeeId, amount, currency, description}` |
| Document expiry | `POST /employer/hr/documents` with `{employeeId, name, expiresOn}`. This endpoint tracks compliance metadata; it does not upload the document bytes. |
| Interview | Create an interview calendar event, then `POST /employer/hr/interviews` with `{roleId, eventId, candidateName, candidateEmail}` |
| Staffing target | `POST /employer/hr/requisitions` with `{roleId, teamId?, positions: 5}` |
| Department plan | `POST /employer/hr/department-plans/:departmentId` with `{leadUserId?, annualBudget, currency, operationalStatus}` |
| Team capacity | `POST /employer/hr/team-plans/:teamId` with `{plannedCapacity: 10, iconId?}` |
| Payroll period | `POST /employer/hr/payroll` with `{startsOn, endsOn, closesOn, currency}` |
| Payroll line | `POST /employer/hr/payroll-lines/:payrollId` with `{employeeId, gross, deductions}` |
| Birthday/anniversary message | `POST /employer/hr/celebrations/:employeeId` with `{message: "Happy birthday!"}` |

Each source has a paginated `GET /employer/hr/<resource>` and, except celebrations, `PATCH /employer/hr/<resource>/:id`. PATCH accepts partial changes; parent identities cannot be changed. Lists support `employeeId` where applicable, `departmentId` for employees, `payrollId` for payroll lines, `date` for attendance and `status` for decision/payroll/requisition records. Document/interview lists support `search`.

General source detail: `GET /employer/hr/records/:kind/:id`. Specialized employee, role and payroll detail routes return calculated statistics.

## Decisions and calendar actions

Approve or decline one or several records atomically:

`POST /employer/hr/leave/decisions` (also `attendance`, `reviews`, `expenses`)

```json
{"ids":["f91c8019-92a8-4714-bf0a-00f3ff5520df"],"status":"approved"}
```

Declining requires `reason`. Leave also supports `status: "cancelled"`. Own approvals are blocked; all changes in a batch roll back if any item fails. Replaying a successful decision does not create another event or email.

`POST /employer/hr/approval-chains` with `{kind: "leave", approverIds: [firstUserId, secondUserId]}` configures sequential approval for **new** requests. The backend snapshots the chain, checks every approver's permission, records each step and notifies the next approver. Intermediate approvals leave the request pending. Empty chains use the relevant approval permission directly. `GET /employer/hr/approval-chains` returns configured chains.

A declined record can be reopened through `POST /employer/hr/requests/:kind/:id/resubmit`, then corrected via PATCH. This applies the current approval chain. Once someone approves a step, its request data cannot be edited.

Other actions:

- `POST /employer/hr/documents/:id/request-update`
- `POST /employer/hr/documents/request-updates` with `{ids: [...]}`
- `POST /employer/hr/documents/:id/dismiss`
- `POST /employer/hr/requisitions/:id/close`
- `POST /employer/hr/payroll/:id/finalize`
- `POST /employer/hr/calendar/:eventId/rsvp` with `{response: "accepted"}`; only changes the signed-in attendee's entry.

Payroll finalization records an approved payroll result; **it does not transfer money, submit tax returns, or call a banking provider**. Finalized lines cannot be edited. Gross amounts and deductions must come from the employer's payroll inputs.

## Calendar and live activity

The frontend uses the same event data for day/week/month views. Request the visible range, treat `endsAt` as exclusive, render times in the event/workspace timezone, and place `allDay` events in the all-day lane. Events spanning midnight/week boundaries are included by overlap, not only by their start date.

First-day events, approved leave and performance reviews are maintained from HR records. Birthdays and work anniversaries are generated for requested calendar ranges, including year changes. February 29 milestones use February 28 in non-leap years. Repeated reads do not create duplicate events. Source-generated events are edited through their HR source; manual events retain calendar CRUD.

For live activity, use `refreshAfterSeconds: 15` from the activity response to refresh the first page, deduplicate by activity `id`, and keep `nextCursor` for older pages. This is polling and works on serverless deployments without a permanently open SSE connection. The frontend must implement that refresh timer. The dashboard includes only the workspace-local **today** activity range.

Use returned action names to show buttons. Decisions/actions still recheck permissions on the backend; hiding a button is not authorization.

## Notifications

HR updates and decisions queue messages into the existing durable notification outbox. The existing notification worker additionally queues due/overdue document, payroll, review and employee milestone reminders. Daily deduplication prevents repeated worker invocations sending duplicate reminders. Activity/reminder preferences are respected. The worker must continue to be scheduled in deployment; no new SMTP provider is required.

Configure existing `SMTP_*`, `MAIL_FROM`, `NOTIFICATION_FRONTEND_URL` and worker authentication as before. `MAIL_FROM` remains a plain verified email address (for example `notifications@huppr.app`), matching the current backend validation. Supabase Auth still sends authentication OTP/reset emails through its configured SMTP. These HR notifications use the application's outbox worker.

## Optional Zoom integration

`POST /employer/hr/calendar/:eventId/zoom` creates and attaches a meeting to an existing future timed event. Configure **that workspace's own** Zoom Server-to-Server OAuth app in a backend-only `ZOOM_WORKSPACES_JSON` environment value:

```json
{"organization-uuid":{"accountId":"ACCOUNT_ID","clientId":"CLIENT_ID","clientSecret":"CLIENT_SECRET","hostUserId":"host@example.com"}}
```

The app needs Zoom permission to create meetings for the configured host. Authentication and requests have deadlines. Only the attendee join URL is returned; the host start URL is never exposed. A persisted claim prevents concurrent duplicates. After an ambiguous provider/network failure, an administrator must reconcile the claim in `hr_zoom_meetings` with Zoom before retrying. This deliberately avoids blind duplicate creation.

Zoom integration was implemented against [Zoom's official API documentation](https://developers.zoom.us/docs/api/using-zoom-apis/) and [Meetings API](https://developers.zoom.us/docs/api/meetings/). Without workspace credentials it returns a clear 503 configuration error. Automated tests mock Zoom; a real provider smoke test requires the configured account.
